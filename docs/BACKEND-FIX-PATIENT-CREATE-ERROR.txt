2) PAYLOAD ENVIADO POR FRONTEND
================================================================================

El frontend envía un POST con la estructura completa de Patient (JSON):

```json
{
  "id": 0,
  "userId": 3,
  "assignedDoctorId": 5,
  "tenantId": null,
  "subscriptionId": null,
  "firstName": "jose",
  "lastName": "perez",
  "dni": "12345678",
  "birthDate": "1990-05-15",
  "gender": "male",
  "phone": "987654321",
  "address": "Av. Lima 123",
  "weight": 0,
  "height": 0,
  "bmi": 0,
  "emergencyContact": {
    "name": "",
    "relationship": "",
    "phone": ""
  }
}
```

CAMPOS OBLIGATORIOS:
- `userId`: FK al user recién creado (DEBE existir en tabla users)
- `firstName`, `lastName`: datos del paciente
- `dni`: documento de identidad (único por paciente)
- `birthDate`: fecha de nacimiento (ISO 8601 o YYYY-MM-DD)
- `gender`: "male" | "female" | "other"
- `phone`: teléfono de contacto
- `address`: dirección

CAMPOS OPCIONALES (pueden ser null o 0):
- `assignedDoctorId`: FK al doctor (puede ser null si no hay asignación)
- `tenantId`: FK al hospital/tenant (null para pacientes independientes B2C)
- `subscriptionId`: FK a subscription (null hasta que pague)
- `weight`, `height`, `bmi`: pueden ser 0 o null inicialmente
- `emergencyContact`: puede tener campos vacíos inicialmente

CAMPO PROBLEMÁTICO:
- `id: 0` — algunos backends rechazan si ven un `id` en el body de un POST create.

================================================================================
3) CAUSAS PROBABLES DEL ERROR 500
================================================================================

Analiza TU BACKEND y revisa si alguna de estas causas aplica:

[ ] 3.1 — Campo `id` en body causa conflicto
    - Algunos frameworks (Spring Data REST, Rails) rechazan POST con `id` presente.
    - Solución: ignorar el campo `id` en el DTO de creación, o validar que sea 0/null.

[ ] 3.2 — Constraint violations (base de datos)
    - ¿Tienes unique constraint en `dni` y el DNI ya existe?
    - ¿Tienes FK constraint en `userId` y el ID 3 no existe en tabla users?
    - ¿Tienes FK constraint en `assignedDoctorId` y el ID 5 no existe en tabla doctors?
    - Solución: validar FKs antes de INSERT; retornar 400 con mensaje claro.

[ ] 3.3 — Campo `emergencyContact` como JSON/JSONB
    - ¿Tu backend acepta campo `emergencyContact` como objeto JSON en Postgres/MySQL?
    - ¿Falla la deserialización del objeto anidado?
    - Solución: asegurar que el DTO/Entity mapee correctamente `emergencyContact` a JSON column.

[ ] 3.4 — Validaciones de entrada fallando
    - ¿Tu DTO valida que `firstName`, `lastName`, `dni` no estén vacíos?
    - ¿Validas formato de `birthDate` (debe ser fecha válida)?
    - ¿Validas que `gender` sea uno de los valores permitidos?
    - Solución: retornar 400 Bad Request con mensaje claro si validación falla.

[ ] 3.5 — Tipo de dato incorrecto
    - Frontend envía `assignedDoctorId`, `tenantId`, `subscriptionId` como NUMBER o null.
    - ¿Tu backend espera UUID/String en lugar de INTEGER?
    - Solución: si son UUIDs, frontend debe enviar strings; o backend debe aceptar int/null.

[ ] 3.6 — Campos opcionales como null vs ausentes
    - ¿Tu backend requiere que los campos opcionales estén AUSENTES en lugar de null?
    - Por ejemplo, si `tenantId: null`, ¿tu ORM intenta validar una FK que no existe?
    - Solución: configurar nullable en el Entity/DTO correctamente:
      ```java
      @Column(name = "tenant_id", nullable = true)
      private Long tenantId; // acepta null
      ```

[ ] 3.7 — Cálculo de BMI falla
    - Si tu backend calcula BMI automáticamente y `weight=0` o `height=0`, puede lanzar ArithmeticException (división por 0).
    - Solución: validar que weight > 0 y height > 0 ANTES de calcular BMI; o permitir BMI=0 para perfiles incompletos.

[ ] 3.8 — Campo `birthDate` formato incorrecto
    - Frontend envía: "1990-05-15" (YYYY-MM-DD).
    - ¿Tu backend espera otro formato o falla al parsear?
    - Solución: aceptar ISO 8601 estándar (YYYY-MM-DD o YYYY-MM-DDTHH:mm:ss.sssZ).

[ ] 3.9 — Errores de logging/stack trace ocultos
    - Tu backend devuelve 500 pero NO logea el stack trace completo.
    - Solución: revisar logs del servidor, activar modo debug, capturar exception y loguear mensaje + stack trace.

   public ResponseEntity<PatientResource> createPatient(
       @RequestBody @Valid CreatePatientRequest request
   ) {
       // Validate userId exists
       User user = userRepository.findById(request.getUserId())
           .orElseThrow(() -> new BadRequestException("User not found: " + request.getUserId()));
       
       // Validate assignedDoctorId if provided
       if (request.getAssignedDoctorId() != null) {
           doctorRepository.findById(request.getAssignedDoctorId())
               .orElseThrow(() -> new BadRequestException("Doctor not found: " + request.getAssignedDoctorId()));
       }
       
       // Check if DNI already exists

           throw new ConflictException("DNI already exists: " + request.getDni());
       }

       patient.setUserId(request.getUserId());

       patient.setTenantId(request.getTenantId()); // can be null
       patient.setSubscriptionId(request.getSubscriptionId()); // can be null

7) CONFIGURACIÓN DE CORS (IMPORTANTE)

Spring Boot ejemplo:
```java
@Configuration
public class CorsConfig {
    @Bean
    public WebMvcConfigurer corsConfigurer() {
        return new WebMvcConfigurer() {
            @Override
            public void addCorsMappings(CorsRegistry registry) {
                registry.addMapping("/api/**")
                    .allowedOrigins("http://localhost:4200", "https://your-frontend.vercel.app")
                    .allowedMethods("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS")
                    .allowedHeaders("*")
                    .allowCredentials(true);
            }
        };
    }
}
```
