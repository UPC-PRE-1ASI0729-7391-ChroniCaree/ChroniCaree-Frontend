1.1 POST /authentication/sign-up
---------------------------------
Propósito: Crear user genérico (paciente o doctor independiente)
URL: POST /api/v1/authentication/sign-up

Request Body:
```json
{
  "email": "usuario@email.com",
  "password": "password123",
  "firstName": "Juan",
  "lastName": "Pérez",
  "role": "patient"
}
```

Campos:
- email (string, required): correo único
- password (string, required): mínimo 8 caracteres
- firstName (string, required): nombre
- lastName (string, required): apellido
- role (string, required): "patient" | "doctor" | "hospital_admin"

Response Success (201 Created):
```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refreshToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user": {
    "id": 123,
    "email": "usuario@email.com",
    "name": "Juan Pérez",
    "firstName": "Juan",
    "lastName": "Pérez",
    "role": "patient",
    "tenantId": null,
    "doctorId": null
  }
}
```

Validaciones Backend:
✅ Email único (retornar 409 si ya existe)
✅ Password mínimo 8 caracteres
✅ Email formato válido (regex)
✅ Role debe ser valor válido
✅ Hashear password antes de guardar (bcrypt)
✅ Generar tokens JWT con exp time apropiado

Response Errors:
- 400: Validación falla (campo faltante, formato inválido)
- 409: Email ya existe
- 500: Error interno

Ejemplo curl:
```bash
curl -X POST "http://localhost:11083/api/v1/authentication/sign-up" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "test@example.com",
    "password": "password123",
    "firstName": "Test",
    "lastName": "User",
    "role": "patient"
  }'
```

Propósito: Crear user admin + tenant (hospital) en UNA SOLA operación atómica

Campos:

- adminEmail (string, required): correo único del admin
- adminPassword (string, required): contraseña (min 8 chars)
- hospitalName (string, required): nombre del hospital/tenant (único)
- address (string, required): dirección del hospital
- phone (string, required): teléfono de contacto
- ruc (string, optional): RUC/Tax ID del hospital

Response Success (201 Created):
```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refreshToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user": {
    "id": 456,
    "email": "admin@hospital.com",
    "name": "Dr. Carlos López",
    "role": "hospital_admin",
    "tenantId": 789,
    "tenant": {
      "id": 789,
      "name": "Hospital San Juan",
      "address": "Av. Principal 123, Lima",
      "phone": "987654321",
      "email": "admin@hospital.com",
      "status": "pending_subscription",
      "subscriptionId": null,
      "settings": {
        "allowIndependentDoctors": false,
        "requirePatientApproval": true,
        "maxDoctors": 5
      }
    },
    "doctorId": null
  }
}
```

IMPORTANTE - Lógica Backend (TRANSACCIÓN ATÓMICA):
1. Validar que adminEmail no exista
2. Validar que hospitalName no exista
3. BEGIN TRANSACTION
4. Crear User con role="hospital_admin"
5. Crear Tenant asociado al User (adminUserId = user.id)
6. COMMIT TRANSACTION
7. Generar JWT tokens con user.id, tenantId incluido en claims
8. Retornar todo en una sola respuesta

Validaciones Backend:
✅ adminEmail único (409 si existe)
✅ hospitalName único (409 si existe)
✅ adminPassword min 8 caracteres
✅ Hashear password antes de guardar
✅ Crear tenant.status = "pending_subscription" (cambiará a "active" al pagar)
✅ tenant.subscriptionId = null inicialmente
✅ settings con valores por defecto según plan (p. ej. maxDoctors: 5 para básico)

Response Errors:
- 400: Validación falla
- 409: Email o hospitalName ya existen
- 500: Error interno (rollback transacción)

- height (number, nullable): altura en metros (puede ser 0 o null)
- bmi (number, nullable): calculado automáticamente o 0
- emergencyContact (object, nullable): contacto de emergencia (puede tener campos vacíos)

```java
@PutMapping("/{id}")
public ResponseEntity<TenantResource> updateTenant(
    @PathVariable Long id,
    @RequestBody @Valid UpdateTenantRequest request
) {
    // 1. Buscar tenant existente
    Tenant tenant = tenantRepository.findById(id)
        .orElseThrow(() -> new ResourceNotFoundException("Tenant not found"));
    
    // 2. Validar FKs si cambiaron
    if (request.getSubscriptionId() != null) {
        subscriptionRepository.findById(request.getSubscriptionId())
            .orElseThrow(() -> new BadRequestException("Subscription not found"));
    }
    
    // 3. Actualizar campos (NO usar id del body, usar el de la URL)
    tenant.setName(request.getName());
    tenant.setAddress(request.getAddress());
    tenant.setPhone(request.getPhone());
    tenant.setEmail(request.getEmail());
    tenant.setStatus(request.getStatus());
    tenant.setSubscriptionId(request.getSubscriptionId());
    tenant.setSettings(request.getSettings());
    // adminUserId y registrationDate NO deberían cambiar
    
    // 4. Persistir
    Tenant updated = tenantRepository.save(tenant);
    
    // 5. Retornar
    return ResponseEntity.ok(toResource(updated));
}
```

- 500: Error interno (EVITAR - retornar 400 con mensaje claro)

6.1 CORS
--------
Configuración CORS para desarrollo y producción:

Orígenes permitidos:
- http://localhost:4200 (desarrollo frontend)
- https://chornicare-frontend-production.vercel.app (producción frontend)
- https://tu-dominio-custom.com (si aplica)

Headers permitidos: Content-Type, Authorization, Stripe-Signature

Credentials: true (para enviar cookies si las usas)

Spring Boot ejemplo:
```java
@Configuration
public class CorsConfig {
    @Bean
    public WebMvcConfigurer corsConfigurer() {
        return new WebMvcConfigurer() {
            @Override
            public void addCorsMappings(CorsRegistry registry) {
                registry.addMapping("/api/**")
                    .allowedOrigins(
                        "http://localhost:4200",
                        "https://chornicare-frontend-production.vercel.app"
                    )
                    .allowedMethods("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS")
                    .allowedHeaders("*")
                    .allowCredentials(true)
                    .maxAge(3600);
            }
        };
    }
}
```

Node.js/Express ejemplo:
```javascript
const cors = require('cors');

app.use(cors({

    'http://localhost:4200',

  ],

  credentials: true
}));
```

6.2 Formato de Errores
-----------------------
Todos los endpoints deben retornar errores en formato JSON consistente:

```json
{
  "timestamp": "2025-12-06T10:30:00.000Z",
  "status": 400,
  "error": "Bad Request",
  "message": "User with id 3 does not exist",
  "path": "/api/v1/patients",
  "details": {
    "field": "userId",
    "rejectedValue": 3
  }
}
```

Campos:
- timestamp (string): ISO 8601
- status (number): código HTTP
- error (string): nombre del error
- message (string): mensaje descriptivo (user-friendly)
- path (string): endpoint que falló
- details (object, optional): detalles adicionales

IMPORTANTE:
- NUNCA exponer stack traces en producción
- Loguear stack traces completos en logs del servidor
- Retornar mensajes claros y accionables al frontend
- Usar códigos HTTP apropiados:
  - 400: Bad Request (validación falla, datos inválidos)
  - 401: Unauthorized (no autenticado, token inválido)
  - 403: Forbidden (autenticado pero sin permisos)
  - 404: Not Found (recurso no existe)
  - 409: Conflict (unique constraint violation, email/dni ya existe)
  - 422: Unprocessable Entity (violación de reglas de negocio)
  - 500: Internal Server Error (error inesperado del servidor)

--------------------------------------------------------------------------------
6.3 Autenticación JWT
----------------------
Todos los endpoints protegidos requieren JWT en header:
Authorization: Bearer <token>

JWT Payload (claims) debe incluir:
```json
{
  "sub": 123,
  "email": "user@example.com",
  "role": "patient",
  "tenantId": 1,
  "doctorId": null,
  "iat": 1701878400,
  "exp": 1701882000
}
```

Claims:
- sub (subject): user.id
- email: user.email
- role: user.role ("patient" | "doctor" | "hospital_admin")
- tenantId: user.tenantId (null si no aplica)
- doctorId: user.doctorId (null si no es doctor)
- iat (issued at): timestamp de emisión
- exp (expiration): timestamp de expiración

Tiempos de expiración recomendados:
- accessToken: 15 minutos a 1 hora
- refreshToken: 7 días a 30 días

Validación en cada request:
✅ Token presente en header
✅ Token válido (firma correcta)
✅ Token no expirado
✅ User existe y no está suspendido
✅ Permisos apropiados para el endpoint

9. TROUBLESHOOTING COMÚN
================================================================================

Problema: PUT /tenants devuelve 500
Causa: Backend rechaza campo `id` en body, o falla al mapear `settings` JSON
Solución: Ignorar `id` del body; mapear `settings` como JSONB; validar FKs

Problema: POST /patients devuelve 500
Causa: Campo `id: 0` causa conflicto; o emergencyContact no mapea
Solución: Ignorar `id` del body; mapear emergencyContact como JSONB

Problema: CORS error en frontend
Causa: Backend no acepta origen http://localhost:4200
Solución: Configurar CORS con origen permitido

Problema: JWT inválido o expirado
Causa: Token exp pasado; o refresh token no implementado
Solución: Implementar refresh token endpoint; frontend debe renovar token

Problema: Unique constraint violation no retorna 409
Causa: Backend retorna 500 genérico
Solución: Catch ConstraintViolationException y retornar 409 con mensaje

Problema: FK violation no retorna 400
Causa: Backend retorna 500 genérico
Solución: Validar FKs ANTES de INSERT/UPDATE; retornar 400 si no existe
